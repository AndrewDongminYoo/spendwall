## Scope and ownership

The root owns all source edits, staging, commits and verification.
Inspect `apps/firewall/src/dashboard/server.ts`, `scripts/dashboard.mjs`, the dashboard build, existing migrations and current HTTP/database tests.
Expected edits are a small explicit hosted-server configuration, a separate hosted launcher, `Dockerfile`, `.dockerignore`, `render.yaml`, focused hosting tests, package scripts if needed, and `docs/hosting.md` plus affected README/dashboard guidance.
Keep changes out of token management, W0 payment routing, mobile platforms and existing applied SQL migrations.
No new dependency is planned; justify any demonstrated need before adding one and regenerate the lockfile with the pinned package manager.

## Steps and evidence

1. Confirm the preparation-only direction and record it in Git-local state.
   Verify the exact base and provider documentation; identify managed-database permissions as an unverified deployment prerequisite.
2. Write failing real-HTTP tests for explicit hosted origin, direct and forwarded Host/Origin spoofing, missing access credential and forbidden policy/mutation routes.
   Keep the local-server contract unchanged; implement the smallest hosted configuration and launcher that pass these tests.
3. Add minimal readiness and graceful shutdown behavior with failure-path checks.
   Verify no credential, policy input or internal database address appears in health/error responses.
4. Build a pinned runtime image that installs frozen dependencies and compiles the dashboard without copying private configuration, local ledgers or caches.
   Keep frontend assets unavailable through the hosted entrypoint until licence integration and release are approved separately.
   Add a deployment template with automatic deployment disabled, explicit secrets and a private database connection.
   Do not create or sync provider resources.
5. Add database provisioning and credential-separation instructions using existing SQL contracts.
   Verify restricted runtime behavior on disposable PostgreSQL; mark actual Render permissions as pending until an authorized provider check is possible.
6. Run the image against disposable synthetic data with populated and empty snapshots, rejected unauthorized requests, unavailable database and restart/shutdown scenarios.
   Check `uptime` before a heavy build and run one heavy job at a time.
   Keep the test listener local; do not issue trial keys or call live providers.
7. Update README and deployment documentation in the same PR, distinguishing preparation from a public service and from completed issue 20 acceptance.
   Run `pnpm check`, explicit image smoke checks, `trunk check --all --no-fix` and `docker compose --env-file .env.example config --quiet`.
8. Perform independent network/authorization and image/database-boundary review, then repair confirmed findings and rerun affected checks.
   Commit by concern, push, open a PR with `Refs #20`, and complete current-head code/security review and CI under the recorded budget.
9. Request operator merge once technical gates pass, without deploying.
   Before any later live release, present the exact account, region, service list, bill estimate, valid licence evidence and rollback path for explicit approval.

# Human approval recording with synthetic or PayPal sandbox payments

`pnpm demo:recording` composes the existing loopback approval API with the demo's PostgreSQL audit/approval tables, trusted context resolver, deterministic policy and, by default, a synthetic refund executor. Without `--paypal-sandbox` it never calls PayPal, and it never calls an AI provider. [PayPal sandbox mode](#paypal-sandbox-mode) is an explicit opt-in that performs one real sandbox refund per approval. The ordinary `pnpm demo` still runs its five recorded scenarios with scripted approval.

This prepares the server side of scene 4. On 2026-10-27 an iPhone 16 Pro installed with the personal Firebase/APNs configuration and development signing reached this command through the tailnet HTTPS forwarder, received a real push, approved with Face ID and observed a PayPal sandbox refund ([#15](https://github.com/AndrewDongminYoo/spendwall/issues/15)). Firebase configuration files, Google ADC credentials and the Tailscale certificate stay outside the repository. Android and the remaining device cases are tracked in [#103](https://github.com/AndrewDongminYoo/spendwall/issues/103). Do not describe the automated fixture as a physical-device test.

## Reproduce locally without device credentials

Use Node from `.node-version`, pnpm from `package.json`, and a running Docker daemon with `postgres:17-alpine` available:

```sh
pnpm install --frozen-lockfile
pnpm test:recording
pnpm test:approval-api
pnpm demo
```

`test:recording` creates disposable loopback PostgreSQL containers and uses the real approval HTTP API, local payment fixtures and a fake notifier. Its enrollment material, signing keys, JWTs and notification addresses belong only to disposable synthetic instances. They grant no access to an operator device, Firebase, Apple or PayPal. Nothing is printed for enrollment or copied into a real configuration.

The tests verify registration before request creation, stored matched rule `rules.v1:1`, authoritative USD 60.00/customer/merchant facts, pending with zero executions, incorrect hash rejection, concurrent/repeated approval with exactly one execution ID and completed result, denial, changed policy/customer, exact Host/Origin rejection, no HTTP request-creation endpoint, CLI result lookup and cleanup. Existing approval API tests additionally cover expiry, revocation, delivery retries and execution recovery. The sandbox-mode tests serve the token, capture, order and refund endpoints from the same fixture. They verify one refund POST under the stored execution ID, one retry under the same ID after a 401 that counts as one submission, none on denial, expiry, an already refunded capture or a capture that needs no approval, and that the default mode makes no PayPal environment lookup or fetch.

## Trusted configuration for a later operator rehearsal

No device enrollment credential is generated by the recording command. After a separately authorized provisioning step, supply an absolute path to a private JSON file outside Git, with owner-only filesystem permissions. It has this shape; the placeholders below are intentionally unusable:

The CLI enforces a regular file owned by its effective operating-system user with no group/other permission bits (for example, `0600` or read-only `0400`). It rejects final-component symbolic links, directories, FIFOs and unsafe ownership/modes; it never changes permissions or ownership for you. Each initial load and `devices` reload opens without following the final symlink, validates the opened descriptor before reading that same descriptor, and rechecks its metadata before parsing. A pathname swap cannot substitute a second file between validation and reading; observed inode, content-metadata or permission changes fail closed. Systems without the required Unix ownership/open flags are refused. Keep the containing directory private and do not grant access through filesystem ACLs; this mode-bit check does not inspect extended ACL entries.

The regression tests exercise real file modes/types and path replacement. The different-owner case uses a simulated effective UID without changing any real file owner; it is not a multi-user OS acceptance test.

```json
{
  "identityKey": "<independent 64-character hexadecimal identity key>",
  "signingKey": "<different 64-character hexadecimal signing key>",
  "port": 3002,
  "devices": [
    {
      "deviceId": "<separately provisioned device ID>",
      "agentId": "demo-support",
      "enrollmentHash": "<SHA-256 digest of its private one-use enrollment credential>"
    }
  ]
}
```

The raw enrollment credential, JWT and FCM registration token do not belong in this file. See [provisioning and JWTs](approval-api.md#provisioning-and-jwts) for the existing contract. Device IDs and digests must already be provisioned; this document does not issue or register one. Omitting `port` selects an available loopback port, which the command prints. The configuration cannot change the bind address, Host/Origin checks or AI behavior; its optional `sandbox` object selects the PayPal sandbox only together with `--paypal-sandbox`.

```sh
pnpm demo:recording /absolute/private/config.json
```

The default explicitly prints `NOTIFICATIONS DISABLED`; it needs no Google credentials and performs no real push. For automated local rehearsal, use `pnpm test:recording` rather than putting its fixture credential into this configuration.

The command starts its own disposable PostgreSQL container/database, applies migrations `001`, `002`, `003`, `004`, `007` and `011`, creates a restricted application login, opens a temporary refund ledger and starts `startApproverServer`. It ignores the repository `.env` and `ANTHROPIC_API_KEY`; without `--paypal-sandbox` it also ignores ambient PayPal keys. It accepts no existing database URL or live-payment option.

The server prints its loopback URL and waits for an active registered device assigned to `demo-support`. Only then does the trusted runner resolve `DEMO_CAPTURE_00002` from the recorded capture/order facts and current ticket customer and call the existing policy/reservation/approval service. The default demo policy requires approval because the authoritative amount is USD 60.00, above USD 20. The console prints:

```text
HUMAN APPROVAL RECORDING / SYNTHETIC PAYMENTS / NO LIVE PAYPAL OR AI
pending_approval: <approval UUID>; synthetic executions=0
```

The pending request is available through the authenticated existing list/detail endpoints. No timeout, console confirmation or agent tool automatically approves it. Approval must arrive through the existing authenticated `/approvals/:id/decision` route. On approve, trusted refresh re-reads policy and ticket, invalidates cached capture facts and resolves the original capture again. Stored request UUID, action, identities, amount and payment facts remain subject to the existing binding, expiry, authority and execution claim checks.

After a successful human decision, the executor ledger and PostgreSQL approval/audit/reconciliation records hold one synthetic result. The console prints `execution_state: succeeded` in JSON and `synthetic executions=1`. Repeated approval retains the same execution ID. Denial or expiry keeps execution at zero; a failed refresh leaves approval unresolved and performs no refund. The server stays available after the result so the phone can re-fetch detail. Press Ctrl+C to close it and remove its container and temporary ledger (exit status 130; SIGTERM uses 143).

All recording state is disposable. This is not restart recovery for an operator session. Restarting loses approvals, device registrations, audit rows, synthetic provider state and executor ledger. Re-register before the next run and never reuse recording enrollment credentials for a real service. For a persistent deployment, retain the stable DB, identity/signing keys and executor ledger together under the existing approval API contract instead.

## PayPal sandbox mode

`--paypal-sandbox` replaces the synthetic payment fixture with the PayPal sandbox for one run, and it performs a **real sandbox refund once per approval**. The refund executor and the context resolver hard-code `https://api-m.sandbox.paypal.com`; this composition has no live PayPal path. The automated tests serve the sandbox endpoints from the synthetic fixture. On 2026-10-27 this mode ran against the real sandbox once: a phone approval refunded a buyer-approved USD 60.00 capture ([#15](https://github.com/AndrewDongminYoo/spendwall/issues/15)). That run needed the 5-second context freshness window from [#102](https://github.com/AndrewDongminYoo/spendwall/pull/102), because the sandbox lookups took about 2.2–2.5 seconds.

Prerequisites, none of which the command creates:

1. Sandbox REST app credentials as `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET` in the process environment. The command reads them only with the flag, and it checks that both are set before Docker starts.
2. A buyer-approved `COMPLETED` sandbox capture above USD 20 whose order has a `payer.payer_id`. The resolver binds the customer to that payer, so the seeded card captures, whose orders have no payer, cannot be used.
3. The capture's payee merchant ID and the merchant email.

Add a `sandbox` object to the private config. All four keys are required and unknown keys are refused. `captureId` is 15–32 letters, digits, `_` or `-`; `payerId` and `merchantId` are 1–128 of the same characters; `merchantEmail` must be a valid email address:

```json
{
  "sandbox": {
    "captureId": "<buyer-approved sandbox capture ID>",
    "payerId": "<payer ID of that capture's order>",
    "merchantId": "<payee merchant ID>",
    "merchantEmail": "<merchant email>"
  }
}
```

```sh
pnpm demo:recording /absolute/private/config.json --paypal-sandbox
pnpm demo:recording /absolute/private/config.json --fcm approved-project-id --paypal-sandbox
```

The flag without a `sandbox` object, a `sandbox` object without the flag, or missing credentials fails with the generic `Recording unavailable.` message before the banner and before Docker starts.

The trusted ticket comes from the config: the customer is `payerId` and the scope is exactly `captureId`. `tickets/approval.json` is not read. Policy, the approval API, approval binding, refresh-before-execute and reconciliation are unchanged. On approve, refresh re-reads the capture and its order. A capture that was refunded in the meantime fails refresh and submits no refund. The executor sends the refund with the stored execution ID as `PayPal-Request-Id`, so concurrent or repeated approvals produce one refund.

If the policy does not require approval, for example because the capture is USD 20 or less, the command prints `Recording policy did not require approval; no sandbox refund was created.` and exits with status 1. It creates no approval and no refund.

The console prints:

```text
HUMAN APPROVAL RECORDING / PAYPAL SANDBOX REFUND / NO LIVE PAYPAL OR AI
pending_approval: <approval UUID>; sandbox refund submissions=0
SANDBOX REFUND RESULT: approval=approved; execution=succeeded; refund=<sandbox refund ID> COMPLETED; sandbox refund submissions=1
```

`sandbox refund submissions` counts the distinct `PayPal-Request-Id` values sent to the refund route, so a retry after a 401 is not counted twice; a refund POST without that header would count on its own. The console never prints tokens, credentials, the payer ID or provider error bodies. The executor ledger stays in the run's temporary directory and is removed on exit, together with the disposable approval database, because a kept ledger could not recover a run whose approvals are gone. The sandbox refund itself remains in PayPal. A later run against the same capture fails at trusted resolution, because nothing remains to refund.

## iOS Simulator rehearsal without Firebase

`apps/approver/lib/main_synthetic.dart` is a debug-only entrypoint for a mock-data rehearsal on an iOS Simulator. It skips Firebase, registers the fixed push address `synthetic-simulator-push` and allows the loopback HTTP origin; biometrics, secure storage and the approval API stay real. It is not push, physical-device or sandbox evidence, and the result is still a synthetic refund.

Start the recording server with a private configuration as described above, then run the app on a booted Simulator from `apps/approver`. On macOS 27 the Simulator app is replaced by DeviceHub (`/Applications/Xcode.app/Contents/Applications/DeviceHub.app`), which shows and controls the booted device:

```sh
flutter run -t lib/main_synthetic.dart -d <simulator UDID>
```

Enroll Face ID in the Simulator before connecting, because enrollment and decisions are disabled without available biometrics. Without the device menu, `xcrun simctl spawn <UDID> notifyutil -s com.apple.BiometricKit.enrollmentChanged 1` followed by `xcrun simctl spawn <UDID> notifyutil -p com.apple.BiometricKit.enrollmentChanged` enrolls it.

The Simulator pasteboard did not receive `xcrun simctl pbcopy` content in DeviceHub, so the entrypoint can enroll itself at launch. Write a private owner-only JSON file outside Git with `SPENDWALL_ENDPOINT` (`http://127.0.0.1:<port>`), `SPENDWALL_DEVICE_ID` and `SPENDWALL_ENROLLMENT` (the disposable one-use credential), then add `--dart-define-from-file=<that file>` to the `flutter run` command. The values are compiled into that debug build, so use this only with a recording credential. Without them, the app shows the normal enrollment form.

The server creates its USD 60.00 request only after registration, and the 15-minute session and approval TTL start then. Because no push is sent, tap refresh in the queue to show the request. When the app asks for confirmation, send a Face ID match from the device menu or with `xcrun simctl spawn <UDID> notifyutil -p com.apple.BiometricKit_Sim.pearl.match`.

The app itself shows no synthetic marker. Add the **SYNTHETIC PAYMENTS / HUMAN APPROVAL** label from scene 4 as a caption in the edited recording and keep it visible throughout.

## Scene 4 prerequisites and filming order

These are operator tasks, not actions performed by the implementation; the operator completed them for an iPhone on 2026-10-27 ([#15](https://github.com/AndrewDongminYoo/spendwall/issues/15)):

1. Create an approved personal Spendwall Firebase project, register the matching iOS app and configure its APNs relationship and private Google ADC credentials outside Git. Follow the [approver README](../apps/approver/README.md); native signing, entitlements and installation remain separate work.
2. Prepare the **private HTTPS** phone path over Tailscale. The API still binds only to `127.0.0.1` and keeps its exact loopback Host and Origin checks. An optional in-repository TLS forwarder (`apps/firewall/src/approver/forwarder.ts`) listens only on the Mac's tailnet IPv4 address in `100.64.0.0/10`; it refuses `0.0.0.0`, loopback and LAN addresses at startup. It accepts a request only when Host equals the configured `<name>.ts.net:<port>` exactly (421 otherwise) and refuses any request that carries Origin (403); refused requests never reach the API. Port 443 is refused at startup, because clients omit the default port from Host and the exact match would then fail. It forwards method, path, query, body and end-to-end headers to the loopback API with Host replaced by the API's own loopback host, removes hop-by-hop headers in both directions, answers 502 when the API is unreachable and logs nothing. Operator steps, none of which this repository performs:
   1. Install Tailscale on the Mac and the iPhone and sign both into the same tailnet.
   2. In the tailnet admin console, enable MagicDNS and HTTPS certificates.
   3. On the Mac, run `tailscale cert <name>.ts.net` for the Mac's MagicDNS name. Keep the key file outside Git, owned by the user who runs the recording command, with mode `0600` or `0400`; the CLI applies the same owner-only, no-symlink, regular-file checks to the key as to the private config.
   4. Add a `forward` object to the private config. All five keys are required, unknown keys are refused, `bind` is the Mac's address from `tailscale ip -4`, `port` is 1–65535 but not 443, and the paths are absolute:

      ```json
      {
        "forward": {
          "bind": "100.x.y.z",
          "port": 8443,
          "host": "<name>.ts.net",
          "certFile": "/absolute/path/<name>.ts.net.crt",
          "keyFile": "/absolute/path/<name>.ts.net.key"
        }
      }
      ```

   5. Start `pnpm demo:recording` as usual. After the API is listening it prints `Tailnet HTTPS forwarder: https://<name>.ts.net:<port>` and closes the forwarder together with the API on Ctrl+C. Without `forward`, nothing listens beyond loopback.
   6. Enter `https://<name>.ts.net:<port>` as the server origin in the app.

   The automated tests use a throwaway self-signed certificate on `127.0.0.1` through a test-only seam. A real tailnet, a `tailscale cert` certificate and an iPhone connection were exercised manually on 2026-10-27 ([#15](https://github.com/AndrewDongminYoo/spendwall/issues/15)).

3. Provision the intended device privately, start the recording server and register the phone before creating the request. Registration stores the FCM address and returns a JWT lasting 900 seconds (15 minutes). Expiry requires a newly provisioned one-use credential and re-registration; there is no refresh-token endpoint. The command re-reads only `devices` from the private file so an independently provisioned replacement digest can be supplied during a run; keep the identity/signing keys fixed. Approval TTL is also 15 minutes. Registration readiness checks an active device row, not a still-valid phone JWT, so keep enrollment and filming close together.
4. Only after Firebase/ADC and the private phone path are independently ready, opt into the existing sender explicitly:

   ```sh
   pnpm demo:recording /absolute/private/config.json --fcm approved-project-id
   ```

   The default has no sender. `--fcm` may contact Google using independently configured ADC; it does not generate credentials or configure Firebase/APNs. On 2026-10-27 it delivered a real push to an iPhone ([#15](https://github.com/AndrewDongminYoo/spendwall/issues/15)). The payment side remains synthetic unless `--paypal-sandbox` is also given.

5. Keep an on-screen label **SYNTHETIC PAYMENTS / HUMAN APPROVAL** throughout the scene, including the iPhone shot. Show the real push opening original facts, the matched rule and USD 60.00 amount, the app's local Face ID confirmation, then the returned synthetic execution result. In [PayPal sandbox mode](#paypal-sandbox-mode), use **PAYPAL SANDBOX REFUND / HUMAN APPROVAL** instead, show the capture's own amount and end on the sandbox refund result. A local biometric gate is not server-side biometric attestation.

Creation enqueues notifications only for matching devices registered at that transaction. Later registration has no retroactive push; use the authenticated pending list to discover an existing request. The runner's registration gate prevents that ordering mistake for its initial request. FCM is advisory and at least once; failed push does not approve, execute or remove the pending request. Never use a public API, external create-approval endpoint, public tunnel or changed bind/authorization checks to complete the scene.

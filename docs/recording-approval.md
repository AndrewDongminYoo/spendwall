# Human approval recording with synthetic payments

`pnpm demo:recording` composes the existing loopback approval API with the demo's PostgreSQL audit/approval tables, trusted context resolver, deterministic policy and synthetic refund executor. It never calls PayPal or an AI provider. The ordinary `pnpm demo` still runs its five recorded scenarios with scripted approval.

This prepares the server side of scene 4. Physical iPhone push delivery, Face ID, device installation, Firebase/APNs, signing and a private HTTPS route have **not** been verified. There is no Spendwall Firebase project or working phone route supplied by this change. Do not describe the automated fixture as a physical-device test.

## Reproduce locally without device credentials

Use Node from `.node-version`, pnpm from `package.json`, and a running Docker daemon with `postgres:17-alpine` available:

```sh
pnpm install --frozen-lockfile
pnpm test:recording
pnpm test:approval-api
pnpm demo
```

`test:recording` creates disposable loopback PostgreSQL containers and uses the real approval HTTP API, local payment fixtures and a fake notifier. Its enrollment material, signing keys, JWTs and notification addresses belong only to disposable synthetic instances. They grant no access to an operator device, Firebase, Apple or PayPal. Nothing is printed for enrollment or copied into a real configuration.

The tests verify registration before request creation, stored matched rule `rules.v1:1`, authoritative USD 60.00/customer/merchant facts, pending with zero executions, incorrect hash rejection, concurrent/repeated approval with exactly one execution ID and completed result, denial, changed policy/customer, exact Host/Origin rejection, no HTTP request-creation endpoint, CLI result lookup and cleanup. Existing approval API tests additionally cover expiry, revocation, delivery retries and execution recovery.

## Trusted configuration for a later operator rehearsal

No device enrollment credential is generated by the recording command. After a separately authorized provisioning step, supply an absolute path to a private JSON file outside Git, with owner-only filesystem permissions. It has this shape; the placeholders below are intentionally unusable:

The CLI enforces a regular file owned by its effective operating-system user with no group/other permission bits (for example, `0600` or read-only `0400`). It rejects final-component symbolic links, directories, FIFOs and unsafe ownership/modes; it never changes permissions or ownership for you. Each initial load and `devices` reload opens without following the final symlink, validates the opened descriptor before reading that same descriptor, and rechecks its metadata before parsing. A pathname swap cannot substitute a second file between validation and reading; observed inode, content-metadata or permission changes fail closed. Systems without the required Unix ownership/open flags are refused. Keep the containing directory private and do not grant access through filesystem ACLs; this mode-bit check does not inspect extended ACL entries.

The regression tests exercise real file modes/types and path replacement. The different-owner case uses a simulated effective UID without changing any real file owner; it is not a multi-user OS acceptance test.

```json
{
  "identityKey": "<independent 64-character hexadecimal identity key>",
  "signingKey": "<different 64-character hexadecimal signing key>",
  "port": 3002,
  "devices": [
    {
      "deviceId": "<separately provisioned device ID>",
      "agentId": "demo-support",
      "enrollmentHash": "<SHA-256 digest of its private one-use enrollment credential>"
    }
  ]
}
```

The raw enrollment credential, JWT and FCM registration token do not belong in this file. See [provisioning and JWTs](approval-api.md#provisioning-and-jwts) for the existing contract. Device IDs and digests must already be provisioned; this document does not issue or register one. Omitting `port` selects an available loopback port, which the command prints. The configuration cannot change the bind address, Host/Origin checks, payment provider or AI behavior.

```sh
pnpm demo:recording /absolute/private/config.json
```

The default explicitly prints `NOTIFICATIONS DISABLED`; it needs no Google credentials and performs no real push. For automated local rehearsal, use `pnpm test:recording` rather than putting its fixture credential into this configuration.

The command starts its own disposable PostgreSQL container/database, applies migrations `001`, `002`, `003`, `004`, `007` and `011`, creates a restricted application login, opens a temporary refund ledger and starts `startApproverServer`. It ignores the repository `.env`, ambient PayPal keys and `ANTHROPIC_API_KEY`. It accepts no existing database URL or live-payment option.

The server prints its loopback URL and waits for an active registered device assigned to `demo-support`. Only then does the trusted runner resolve `DEMO_CAPTURE_00002` from the recorded capture/order facts and current ticket customer and call the existing policy/reservation/approval service. The default demo policy requires approval because the authoritative amount is USD 60.00, above USD 20. The console prints:

```text
HUMAN APPROVAL RECORDING / SYNTHETIC PAYMENTS / NO LIVE PAYPAL OR AI
pending_approval: <approval UUID>; synthetic executions=0
```

The pending request is available through the authenticated existing list/detail endpoints. No timeout, console confirmation or agent tool automatically approves it. Approval must arrive through the existing authenticated `/approvals/:id/decision` route. On approve, trusted refresh re-reads policy and ticket, invalidates cached capture facts and resolves the original capture again. Stored request UUID, action, identities, amount and payment facts remain subject to the existing binding, expiry, authority and execution claim checks.

After a successful human decision, the executor ledger and PostgreSQL approval/audit/reconciliation records hold one synthetic result. The console prints `execution_state: succeeded` in JSON and `synthetic executions=1`. Repeated approval retains the same execution ID. Denial or expiry keeps execution at zero; a failed refresh leaves approval unresolved and performs no refund. The server stays available after the result so the phone can re-fetch detail. Press Ctrl+C to close it and remove its container and temporary ledger (exit status 130; SIGTERM uses 143).

All recording state is disposable. This is not restart recovery for an operator session. Restarting loses approvals, device registrations, audit rows, synthetic provider state and executor ledger. Re-register before the next run and never reuse recording enrollment credentials for a real service. For a persistent deployment, retain the stable DB, identity/signing keys and executor ledger together under the existing approval API contract instead.

## iOS Simulator rehearsal without Firebase

`apps/approver/lib/main_synthetic.dart` is a debug-only entrypoint for a mock-data rehearsal on an iOS Simulator. It skips Firebase, registers the fixed push address `synthetic-simulator-push` and allows the loopback HTTP origin; biometrics, secure storage and the approval API stay real. It is not push, physical-device or sandbox evidence, and the result is still a synthetic refund.

Start the recording server with a private configuration as described above, then run the app on a booted Simulator from `apps/approver`. On macOS 27 the Simulator app is replaced by DeviceHub (`/Applications/Xcode.app/Contents/Applications/DeviceHub.app`), which shows and controls the booted device:

```sh
flutter run -t lib/main_synthetic.dart -d <simulator UDID>
```

Enroll Face ID in the Simulator before connecting, because enrollment and decisions are disabled without available biometrics. Without the device menu, `xcrun simctl spawn <UDID> notifyutil -s com.apple.BiometricKit.enrollmentChanged 1` followed by `xcrun simctl spawn <UDID> notifyutil -p com.apple.BiometricKit.enrollmentChanged` enrolls it.

The Simulator pasteboard did not receive `xcrun simctl pbcopy` content in DeviceHub, so the entrypoint can enroll itself at launch. Write a private owner-only JSON file outside Git with `SPENDWALL_ENDPOINT` (`http://127.0.0.1:<port>`), `SPENDWALL_DEVICE_ID` and `SPENDWALL_ENROLLMENT` (the disposable one-use credential), then add `--dart-define-from-file=<that file>` to the `flutter run` command. The values are compiled into that debug build, so use this only with a recording credential. Without them, the app shows the normal enrollment form.

The server creates its USD 60.00 request only after registration, and the 15-minute session and approval TTL start then. Because no push is sent, tap refresh in the queue to show the request. When the app asks for confirmation, send a Face ID match from the device menu or with `xcrun simctl spawn <UDID> notifyutil -p com.apple.BiometricKit_Sim.pearl.match`.

The app itself shows no synthetic marker. Add the **SYNTHETIC PAYMENTS / HUMAN APPROVAL** label from scene 4 as a caption in the edited recording and keep it visible throughout.

## Scene 4 prerequisites and filming order

These are pending operational tasks, not actions performed by the implementation:

1. Create an approved personal Spendwall Firebase project, register the matching iOS app and configure its APNs relationship and private Google ADC credentials outside Git. Follow the [approver README](../apps/approver/README.md); native signing, entitlements and installation remain separate work.
2. Establish a separately reviewed **private HTTPS** phone path. The API must still bind only to `127.0.0.1` and see exactly its own loopback Host and, when present, matching Origin. A VPN alone does not make the phone's loopback reach the Mac or satisfy these checks. A private TLS forwarding design must account for the upstream Host/Origin explicitly without weakening server validation or introducing a public listener/tunnel. No VPN, Tailscale, certificate, proxy or routing configuration is installed here.
3. Provision the intended device privately, start the recording server and register the phone before creating the request. Registration stores the FCM address and returns a JWT lasting 900 seconds (15 minutes). Expiry requires a newly provisioned one-use credential and re-registration; there is no refresh-token endpoint. The command re-reads only `devices` from the private file so an independently provisioned replacement digest can be supplied during a run; keep the identity/signing keys fixed. Approval TTL is also 15 minutes. Registration readiness checks an active device row, not a still-valid phone JWT, so keep enrollment and filming close together.
4. Only after Firebase/ADC and the private phone path are independently ready, opt into the existing sender explicitly:

   ```sh
   pnpm demo:recording /absolute/private/config.json --fcm approved-project-id
   ```

   The default has no sender. `--fcm` may contact Google using independently configured ADC; it does not generate credentials or configure Firebase/APNs. This option was not exercised against Google. The payment side remains synthetic.

5. Keep an on-screen label **SYNTHETIC PAYMENTS / HUMAN APPROVAL** throughout the scene, including the iPhone shot. Show the real push opening original facts, the matched rule and USD 60.00 amount, the app's local Face ID confirmation, then the returned synthetic execution result. A local biometric gate is not server-side biometric attestation.

Creation enqueues notifications only for matching devices registered at that transaction. Later registration has no retroactive push; use the authenticated pending list to discover an existing request. The runner's registration gate prevents that ordering mistake for its initial request. FCM is advisory and at least once; failed push does not approve, execute or remove the pending request. Never use a public API, external create-approval endpoint, public tunnel or changed bind/authorization checks to complete the scene.
